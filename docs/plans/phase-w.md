# Phase W — Web app (Next.js)

> Status: **IN PROGRESS** · drafted 2026-10-26 · ADR-002, ADR-016, ADR-018, ADR-021
> Convention: `[ ]` todo · `[~]` in progress · `[x]` done & verified · `[!]` blocked (reason)
> Shipped as slices W0–W6, one PR each. The contract is frozen (`contract-v1.0`): the web app
> adapts to the API, never the reverse (an API gap is an additive change with tests).

## Goal
The landlord/agency/host dashboard, the read-only owner view, the tenant portal and the
operator console, covering every journey the API supports, usable on a phone, and proven by
Playwright journeys against the real API.

## Key decisions
- **`apps/web`:** Next.js 16 App Router (ADR-021), a **pure client of the API**:
  - all data goes through `@kejasha/api-client` (generated) with TanStack Query;
  - no server-side data access, no database, no secrets;
  - pages are client components behind an auth gate; the Next server only serves the app.
- **Auth:**
  - Better Auth session cookie set by the API. In production web and API share
    `.${APP_DOMAIN}` (cookie domain), and requests use `credentials: 'include'`.
  - CORS and the Origin check already trust `WEB_URL`.
  - Locally: web on `localhost:3000`, API on `localhost:4000` (same-site).
  - The API base URL comes from `NEXT_PUBLIC_API_URL`, falling back to `/v1/meta/config`
    conventions (ADR-016). There is no domain literal in source.
- **UI:**
  - `packages/ui` holds the shadcn/ui components (generated by the shadcn CLI, then owned in the
    repo), Tailwind v4 tokens, and composites (data table, money, date, page header, empty
    states).
  - No hand-built primitives (CLAUDE.md §3).
  - Light/dark themes; mobile-first layouts (caretakers and owners use phones).
- **Forms:** React Hook Form + Zod resolvers using the **same schemas** as the API
  (`@kejasha/contracts`). Server problem+json errors map onto fields (`errors[].path`) or a toast
  (`code`).
- **Money and dates:** cents are formatted only in the UI (`KES 12,345.00`); inputs accept
  shillings and convert to cents; business dates are shown and entered in Africa/Nairobi.
- **Idempotency:** every mutation sends an `Idempotency-Key` generated per form submission, so a
  double click or retry never duplicates a payment or booking.
- **Roles drive navigation:** owner/manager/agent see their modules, caretakers see their
  properties, viewers see dashboard/statements/reports, tenants get `/portal`, operators get
  `/operator`.
- **Billing states:** a banner and route gate for `incomplete`/`past_due`/`suspended`. A 402
  from any write opens the billing page; reads keep working.
- **Testing:**
  - Vitest + Testing Library for components and hooks.
  - **Playwright journeys** run the built web against the real API (Testcontainers-backed
    services in CI), mirroring the API journeys.
  - Axe accessibility checks run on key pages.

## Notes
### W0 (2026-10-26)
- The billing page and the Paystack return page shipped in W0, because the billing banner links
  to them. W5 keeps the rest of account & platform.
- **Hydration guard.** Before React hydrates, a click on Submit makes the browser submit the
  form natively as a GET, putting the email and password in the URL (and so in history and
  logs). Playwright reproduced this after sign-out's full page load. Every form now uses
  `SubmitButton`, which stays disabled until the page is hydrated.
- **Active org.** A new session has no active org, so the shell selects one automatically: the
  org last used in this browser (stored in `localStorage` as a convenience only), else the first
  membership. Onboarding is only for users with no memberships.
- **Locators.** Use role-based locators: on sign-in, "Email" names a tab panel as well as the
  input.
- **Rate limits.** The API allows 20 sign-ups per IP per hour. CI starts with a fresh Redis
  each run. Locally, `make dev-reset-limits` clears the counters. Later journeys sign in as
  seeded users instead of signing up.
- **Dev vs production server.** Against `next dev`, parallel journeys can exceed the 5 s
  navigation expectation while routes compile. CI runs `next build && next start`, where the
  suite passed 24 of 24 times (`--repeat-each 4`).

### W1a (2026-10-26)
- Shared building blocks for every later slice:
  - `DataTable` (TanStack Table v9: sorting over loaded rows, cursor "Load more", error and
    empty states, `hideOnMobile` columns);
  - `usePaged` / `fetchAll` (cursor lists; the API caps `limit` at 100);
  - `useWrite` (one Idempotency-Key per intent, then invalidate and toast);
  - fields: `SelectField` (passes `items` so Base UI shows labels), `MoneyField` (shillings
    typed, cents held), `NumberField`, `DateField`, `TextareaField`; `FormDialog`,
    `ConfirmButton`.
- Create and edit share one field set typed by the Update schema; the Create schema is the
  resolver when creating. A blank optional field sends `undefined` on create and `null` on edit.
- Money displays as the `en-KE` locale writes it (`Ksh 18,000.00`); the money input's prefix
  matches.
- Journeys that need data sign in as the seeded demo users through a Playwright setup project
  (one sign-in per user per run). The CI e2e job now runs `seed`.
- The bulk reading endpoint answers per meter; the round shows each rejection beside its meter
  (`reading_decreased`, `reading_exists`) and keeps the rejected values for correction.

### W1b (2026-10-26)
- Screens:
  - tenants;
  - leases: create with unit and tenant pickers, edit terms, rent change, renew, end, cancel;
  - charges (flat or metered on the unit's meter);
  - invoices (one-off, void), credit notes, statement;
  - deposit settlement (shows the refund due; Kejasha never pays it out);
  - inspections with photos;
  - arrears with "Run billing now"; lease calendar.
- `ComboField` (shadcn Base UI combobox) searches on the server and keeps the chosen option's
  label. Rent and deposit are copied from the chosen unit.
- `PercentField` holds basis points. `MoneyField` and `PercentField` follow values set from
  outside (reset, prefill).
- Navigation that looks like a button is now a real link (`LinkButton`). Base UI's Button gave
  links a button role, so assistive tech announced them as buttons.
- Filter selects use an explicit "all" value: Base UI shows the placeholder for `''`.
- Photo uploads PUT directly to object storage with the API's upload ticket (`lib/upload.ts`).
  The bucket's CORS must allow PUT from the web origin. That is part of the launch checklist
  (R2 bucket setup).
- **Performance note.** Under the parallel e2e journeys (many lease creations at once), one
  `GET /v1/arrears` took 8 s locally; alone it takes 10–135 ms. The k6 run covers arrears reads
  only. When the load test is repeated on the VM before launch, add concurrent lease creation
  to the mix.

### W2 (2026-10-26)
- Screens:
  - payments queue (to match / all, by source) with ranked suggestions, one-tap apply, apply to
    any lease, ignore and unmatch with reasons, receipt PDF;
  - add payments by M-Pesa SMS paste, statement import (CSV, or PDF with password) or
    recorded cash/bank;
  - M-Pesa payment requests (STK) with live status (3 s polling);
  - M-Pesa setup: channels, write-only Daraja keys, register URLs, go-live checklist with
    callback URLs to copy;
  - cash: log by unit with a receipt photo, confirm or reject; payments tab and actions on
    the lease page.
- **API gap closed (additive, contract 1.1.0).** Caretakers could log cash but cannot see
  leases (not over HTTP, not in sync), so they had no way to say whose cash it was.
  `CreateCashCollectionBody` gains an optional `unitId`: the lease covering `receivedOn` is used
  (`422 no_lease_on_unit` otherwise). Caretakers are checked against their properties first, so
  the answer never reveals whether a unit elsewhere is let. Sync push gets it too, since it
  reuses the body. Integration test, spec, client and payments guide updated; oasdiff reports no
  breaking change. Tag `contract-v1.1` after merge.
- STK Push and C2B registration need real Daraja sandbox credentials (launch inputs). The
  screens are built against the contract; the journey covers everything else (SMS by phone and
  by hand, receipt PDF, cash confirmation, channel checklist).
- Receipts open in a new tab from a fetched blob (the request needs the session cookie).
  Headless Chromium downloads PDFs instead of showing them; the journey asserts the download.

### W3 (2026-10-26)
- Screens:
  - **Calendar:** a 21-day multi-unit timeline, coloured by channel. Tap a free day to book it;
    block dates and re-open them.
  - **Bookings:** list; new booking with a live quote (nightly breakdown, cleaning, availability,
    minimum stay with an explicit override) and new or returning guests; booking page with
    check-in, check-out, no-show, cancel, edit, and M-Pesa request / recorded payment for
    direct stays.
  - **Guests**, with repeat recognition.
  - **Unit page (short-stay):** rates and rules, seasons, imported iCal feeds (sync now,
    enable/disable, disconnect, conflicts), upcoming stays.
  - **Expenses**, per unit or property-wide.
  - **Profit report:** per unit, plus a channel comparison (what each platform really costs,
    net per night).
- The sidebar is grouped into sections: Long-term, Short stays, Money, Setup.
- Detail pages show the API's message and a Retry button when loading fails (`QueryFallback`);
  before, they showed a skeleton forever.
- Playwright's assertion timeout is 10 s. Journeys hit a real API and database, and failed
  intermittently at 5 s while this laptop's load average was 25–45 from unrelated apps. With
  one worker, the full suite passed 20/20 locally.

### W4 (2026-10-26)
- Screens:
  - **Maintenance:** active/all lists by priority and property; report a problem (unit or
    common area, photos); ticket page with the status moves the API allows (open ↔ in progress
    → resolved → closed, reopen, cancel; caretakers cannot close or cancel), a timeline with
    photos, assignment (staff or outside fundi) and cost. A final cost becomes an expense.
  - **Compliance:**
    - Monthly Rental Income per landlord (defaults to last month; due date, year-to-date band,
      missing PINs, filing status), with a detail page: per-tenant lines, eRITS CSV,
      record/undo filing, and the difference when receipts change after filing.
    - Tenant PIN register.
    - Licences: add, renew, archive, document upload, expiring/expired flags.
  - **Reports:** owner statements (detail and PDF), rent roll, collections (by method, channel,
    property), occupancy; CSV exports. Read-only owners (viewers) see Reports.
- The sidebar gains Maintenance and an Insights section (Reports, Compliance).
- The ticket's close action is labelled "Close ticket": "Close" clashed with the toast's close
  button for assistive tech (and the test).

## Definition of Done

each role; no hand-written API types; accessibility checks clean on key pages; CI green.
